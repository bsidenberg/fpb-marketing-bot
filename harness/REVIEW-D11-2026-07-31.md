## 1. Verdict on the premise

**The current implementation does not satisfy D-11.** I verified this from the code, not from
last night's write-up, and I agree with last night's reviewer's blocker 5 — but for a reason I
want to state independently rather than defer to their authority (SDR-2 applies to them too).

`expectedDeltaProfitableLeads`'s `waste_removal` branch hard-codes the cap's bypass flag:

```
removed: {
  spend: removedCohort.spend,
  ...
  spendVerified: true, // a measurement derived from fetched rows, never a claim
},
```
(`objective.js:1045`, inside the block that runs whenever `deriveRemovedCohort` returns
`valid: true`.)

`evaluateReallocation` (`objective.js:645-666`) branches entirely on this boolean: `spendVerified
=== true` skips the W-multiple bound outright. The pre-S-08A.1a scalar shape
(`candidate.removed`/`candidate.host`) — the *only* code path that could ever produce
`spendVerified !== true` — is now refused outright at the entry point
(`objective.js:983-988`, `'removed_and_host_scalars_no_longer_accepted_use_rows_contract'`).

**Consequence, checked directly against the code rather than assumed:** every candidate that can
actually reach `evaluateReallocation` today does so with `spendVerified: true`. There is no live
path left by which the W cap's `else` branch (`objective.js:652-665`, the W-multiple clamp) can
ever execute. The cap's code is intact, its ~10 dedicated tests still pass, and it is
unreachable from the sanctioned entry point. This is precisely what D-11's own DECISIONS.md entry
warns against in the abstract ("a real check assumed running because it is configured") applied
to itself. I confirm last night's reviewer's structural finding by independent reading of the
same lines they cite.

**Where I want to sharpen the finding beyond "unreachable," because it changes what the fix must
be:** the deeper problem is not merely that the flag is hard-coded — it's *what the flag is being
used to certify*. A14's original meaning of "verified" was "this number is a real fetched
measurement, not typed by a model." Under the rows contract, every individual row's `cost` field
is indeed a real fetched value (S-07f.0 confirmed the GAQL SELECT and mapper produce real
`resource_name`/`cost`/`conversions`). But `deriveRemovedCohort` and `deriveHostFromRows` do not
just report a number — they *choose a subset of rows to sum*, filtered by `hostCampaignId` and
`expectedSearchTerms` (removed) or `hostCampaignId` alone (host). Design decision #5 in
DECISIONS.md's own S-08A.1a entry states plainly that `expectedSearchTerms`' correctness "is the
CALLER's responsibility, not this pure module's," and `deriveHostFromRows` (`objective.js:894-945`)
performs no cross-check against `expectedSearchTerms` or any completeness signal at all — it sums
whatever rows are present in the caller-supplied `rows` array that happen to match
`hostCampaignId`.

So: every *addend* is a real measurement, but the *set of addends* is still a claim, made by
whoever assembles `rows`/`expectedSearchTerms` before calling the module. `spendVerified: true`
conflates "every number in this sum is real" with "this sum is the right sum" — that is SDR-7
exactly: a true, verified defense (real row-level values) is being read as coverage of a
different threat (attacker-controlled membership) it was never built to answer. Last night's
reviewer's own A15-host-side finding (host membership bound only by campaign, an attack candidate
outscoring real work 13.14 to 3.84) is the live demonstration of this same root cause on a
different axis — I am not re-litigating that finding, only naming why it and the cap's dead-code
problem are the same defect wearing two faces.

**If I am wrong that this is D-11's actual failure mode, the alternative reading is that "the cap
stays" was satisfied by the code existing at all, regardless of reachability.** I reject that
reading: D-11's own stated reason for retention was "the corrected contract is new code that has
never run in production" (`DECISIONS.md`, I-007) — i.e., the cap was kept *specifically as a
backstop for this new derivation path*, not as a backstop for a legacy shape that has now been
deleted. A backstop that cannot reach the one path it was retained to backstop does not satisfy
the decision that retained it, regardless of how the code reads in isolation.

## 2. The requirement

**Source of truth the cap must bound against: cohort membership provenance, not row-value
provenance.** Concretely: `removed.spendVerified` (or whatever gates the W-multiple bypass) must
certify that the *set* of rows summed into `removed` and `host` is the complete, correct set
implied by the action being scored — not merely that each row's numeric fields came from a real
Google Ads API response. Until a signal exists that establishes set-completeness independently of
whoever assembled `rows`/`expectedSearchTerms`, the derived spend must be treated as a **claim**
and the W-multiple bound must apply to it, exactly as it applies to the retired scalar shape.

**Why this source survives the three named attacks, and why row-value provenance alone does
not:**

- **The 18x attack (A14, original).** `removed.spend` was asserted directly, with no rows and no
  membership at all. Under a membership-provenance standard there is nothing to even evaluate as
  "complete" — it fails trivially and the cap applies. Both the old and the new standard catch
  this one; it is not the interesting case.
- **The 167x attack (A15, first S-08A.1 draft).** An account-wide, unfiltered fetch was attached
  to a one-term negative. Row-*value* provenance says nothing wrong here — every row was real.
  Membership provenance catches it directly: the removed side's cross-check against
  `expectedSearchTerms` (closing A15 on the *removed* side, which the current code does do) is a
  first instance of exactly the standard this requirement generalizes — it should also cover the
  *host* side, which today has no equivalent check at all.
- **The 2026-07-28 chat-surface fabrication (campaign-level numbers real, search-term rows
  fabricated).** This is the sharpest case, and it is the one row-value provenance cannot touch
  even in principle: a model narrating a tool call that never ran can hand `objective.js` a
  `rows` array that is internally well-formed (plausible `cost`/`conversions` values, syntactically
  valid `rowId`s) but corresponds to no real fetch at all. `deriveRemovedCohort`/`deriveHostFromRows`
  have no way to detect this from the array's contents — they trust `rows` as given, by design
  (the module is pure, zero I/O, per its own header). The only thing that can close this is a
  `fetchId` that traces back to a **server-persisted fetch record the model cannot mint or
  replay** — which is the exact mechanism S-07f.1 (fetch cache, D-8) exists to build. Today
  `fetchId` is checked only for being a non-empty string (last night's Blocker 3, "correlated
  with nothing on the actual rows") — so the fabrication threat is *currently uncovered by
  anything in this contract*, cap included. Naming this matters because it shows row-value
  provenance is not merely incomplete against membership attacks — it is structurally blind to
  the most severe attack on the list, and the cap's current gating condition (`spendVerified` from
  `deriveRemovedCohort` succeeding) gives that attack a free pass on the one axis (spend
  inflation) the cap exists to bound.

**What the cap must do when this source is unavailable, stale, or un-derivable: fail closed, not
silent-pass.** Concretely, `spendVerified` must default to `false` — not `true` — whenever
membership completeness cannot be established, which is the situation for every candidate today
(no completeness signal is wired at all). This is not a new principle for this codebase; it is
the same posture D-8 already requires elsewhere ("silence and success must not be the same
outcome") and the same posture `evaluateReallocation` itself already takes when host efficiency
is unresolvable (`objective.js:673-684`, `'no_host_efficiency_reallocation_credited_zero'` — it
fails toward giving no credit, not toward giving full credit). The rows contract's current
default runs backwards from that established pattern: it defaults to trusting the derivation
fully (`spendVerified: true`) precisely in the case — a brand-new, never-run-in-production
contract — where D-11 says trust should be lowest.

**Form vs. level (DI-3).** This requirement constrains **form**: what "verified" means and when
the bypass is granted. It does **not** constrain **level**: it says nothing about the value of
`reallocation_max_waste_multiple` (W), which stays at its current CHOSEN value (3) — this is the
null-change migration DI-3 requires, the same move DI-3's own founding case took with
`max_profitable_leads_per_dollar`'s `k=25`. **It does not, by itself, force a level change.** I
flag one place a *new* level could later be introduced and explicitly put it out of this
requirement's scope: if the eventual implementation of a completeness cross-check (e.g. against
`campaign_daily_stats`, or a full-vs-filtered row-count comparison) needs a tolerance — how close
the caller-supplied host aggregate must be to an independently-sourced one to count as "complete"
— that tolerance is a **new standing number**, requiring its own DERIVED/CHOSEN tag and owner
sign-off per §4.3, and must not be silently folded into W or left unlabeled. Naming a value for
it is explicitly out of my scope per this review's own instructions, and I have not proposed one.

## 3. Acceptance test

A specific, writable test, expressed against the module's existing public surface
(`deriveHostFromRows`, `deriveRemovedCohort`, `evaluateReallocation`,
`expectedDeltaProfitableLeads`) — no new infrastructure required to state it, though the
membership-provenance signal it checks for does not exist yet (see §4):

> Construct an honest host campaign with N real fetched rows (varied cost/conversions). Construct
> a second `rows` array that is a **strict subset** of those N rows — e.g., drops every row with
> `conversions > 0`, keeping only the highest-cost zero-conversion rows plus the removed term —
> the exact host-side shape of last night's 13.14-vs-3.84 attack. Run both through
> `expectedDeltaProfitableLeads` with identical `removed`/`expectedSearchTerms`. **Assert:** the
> subset-fed candidate's `score` (via `scoreRecommendation`) does not exceed
> `W × score(honest-full-membership candidate)` — OR the subset-fed candidate is refused outright
> (`delta: null`) for failing a membership-completeness check. Today this test **fails**: the
> subset-fed candidate is unbounded relative to the honest one, because `spendVerified: true` is
> unconditional and the W cap never engages. This is the test last night's reviewer's blocker 3/5
> implies but did not phrase as a bounding assertion — theirs demonstrates the attack succeeds;
> this version states the requirement as a pass/fail line a build session can be held to.

This test is checkable today, on fixtures, without waiting for S-07f.1's fetch-cache work — it
exercises the bound itself, not the eventual provenance mechanism. A second test, gated on
whatever provenance signal is eventually wired (out of scope to specify further here), would
additionally assert that a `rows` array traceable to a real persisted `fetchId` is exempted from
the bound while one that is not remains subject to it.

## 4. Attack on my own proposal

**Model, per the instructions: assume an LLM that names rows and controls any remaining
caller-supplied scalar** — i.e., it can choose `expectedSearchTerms`, and it can influence, directly
or indirectly, which rows end up in the `rows` array (since no session before S-08B/chat.js
integration exists yet to bind that array to an untouched server fetch).

**The attack:** my requirement says "apply the W bound unless membership completeness is
independently verified." But `objective.js` is deliberately **pure — zero I/O** (its own header,
`objective.js:1-9`). It cannot itself fetch a second, independent copy of the host campaign's
rows to compare against. Any "independent" signal I imagine (a `campaign_daily_stats` cross-check,
a full-account row count) has to be supplied by the **caller** — and the caller is exactly the
integration layer (S-08B, or a chat.js wiring) that does not exist yet and that, per the
chat-surface incident, has already been shown capable of narrating fetches that never happened.
If the "independent" signal is just another field on `candidate` — say,
`candidate.hostRowCountFromSeparateQuery` — a sufficiently capable model narrates that field too,
and I have added a check that is defeated by the identical mechanism as the one it was meant to
close.

**Does it fail, or is there a residual gap?** It fails to close the gap completely by itself —
and I want to be explicit that it fails, not paper over it. **The residual gap: no purely
in-module check can distinguish a genuinely independent signal from a second caller-asserted
field, because the module has no channel to the outside world by construction.** The actual
closure has to happen one layer up, at the boundary where `rows` first enters the system —
`fetchSearchTerms` itself (`api/google-ads.js:312`) or a caching layer in front of it (S-07f.1) —
which must mint a `fetchId` server-side, persist the raw fetch, and refuse to accept a `rows`
array on a later turn that doesn't match a stored fetch by that id. **My requirement is therefore
necessary but not sufficient on its own**: it correctly stops `spendVerified` from being a free
pass granted by `objective.js` to its own output, but the thing it hands the decision *to* — a
provenance chain rooted outside the pure module — does not exist yet. Until it does, my
requirement's practical effect is exactly its fail-closed fallback (§2): treat everything as an
unverified claim and apply the W bound universally on this path. That is a real, if blunt,
mitigation today (it at least bounds the damage a membership attack can do, the same way the
original A14 cap bounded the damage a raw assertion could do) — but it is not a closure of A15,
A17, or A19, which remain S-08A.1a.2's to fix at the membership-derivation layer itself, not the
cap's.

## 5. Cost

- **Legitimate large waste-removal actions get under-credited in the interim.** The entire reason
  `spendVerified` was invented (A14, I-002) was to let a genuinely dead search term — zero
  qualified leads, real spend, the textbook eval-E1 case — score its full, disproportionate value
  without being clamped by a lead-share formula that treats zero leads as zero justified spend.
  Reverting to "treat rows-derived spend as an unverified claim by default" reintroduces exactly
  that clamp for every waste-removal candidate until a real provenance chain exists — including
  the honest ones. This is the same tension the original carve-out existed to resolve, now
  reopened deliberately, as a stated tradeoff rather than an oversight.
- **This requirement cannot be closed by editing `objective.js` alone.** Because the module is
  pure and has no I/O, the actual fix — a real, unspoofable membership/provenance signal — has to
  be built at the caller boundary (S-07f.1's fetch cache, and whatever future session wires
  `rows` into `expectedDeltaProfitableLeads` for real, e.g. S-08B or a chat.js integration). That
  means D-11 cannot be fully discharged by a self-contained patch to the scoring module; it
  creates a dependency edge from "D-11 satisfied" to "S-07f.1 lands with a genuine `fetchId`
  verification," which is not how the harness currently sequences these sessions (S-08A.1a.2 is
  scoped to cohort-derivation logic only, and S-07f.1 is scoped to the execute-path staleness
  refusal, not to feeding `objective.js` a provenance signal it can check). This is new
  coordination cost, not implementation cost, and it should be recorded as a harness amendment
  (a new dependency), not discovered mid-build.
- **A blunt fail-closed default is cheap to build and expensive to live with.** Applying the W
  bound unconditionally to every rows-derived candidate (my requirement's practical fallback,
  §2/§4) is a small, local change. But it is also a queue-quality regression versus the contract's
  stated intent for as long as it is the only mitigation in force — real waste-removal
  recommendations will under-score, some may fall below `min_score_threshold`, and Phase A's
  stated goal (surface genuinely wasteful spend for Brian to cut) is weakened exactly while the
  fix is "done." This should be disclosed to Brian as a known, accepted regression at whatever
  session implements it, not silently absorbed into a passing test suite.
